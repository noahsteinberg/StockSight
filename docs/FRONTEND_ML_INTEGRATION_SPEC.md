## 1. Product and current boundary

A user searches for a supported stock, explores observed history, saves it to a
private watchlist, and eventually inspects a clearly defined model signal and
its measured historical reliability. The product does not need a projected
future-price curve. Relative stock ranking is the current research candidate;
absolute up/down prediction has not qualified for serving.

Working today: existing React/Vite pages, hash navigation, sourced daily price/
volume charts, SMA20/RSI14, FastAPI, SQLAlchemy/Alembic, Supabase storage, Auth0
and app-session/private-watchlist code. Production is stocksight-rose.vercel.app.
Hosted data is the historical AAPL sample ending 2017-02-16. Predictions and
performance intentionally show unavailable states. No current quote feed,
automated refresh, approved model artifact, prediction persistence or ML API exists.
Noah reports Auth0 settings were fixed; complete hosted account acceptance still
needs evidence. Do not confuse implemented auth code with freshly verified login.

## 3. Page-by-page behavior

### Analysis: #/analysis?symbol=AAPL

Keep ticker/company search, ranges, price/volume, SMA/RSI, inspection and saving.
Keep observed prices visually separate from a future model signal. A later
compact signal summary can sit below the existing chart with a link to Predictions.
Do not extend the chart with an unvalidated predicted price path.

First increment: existing Analysis remains unchanged except its existing link
continues to open Predictions for the selected symbol. Unsupported symbols keep
the current 404 flow. Stale chart data must not be called live/current.

Later example wording, only if supported by approved real data:

> AAPL — Relative research signal
> Ranked in the top 21% of eligible stocks for the next trading session.
> Inputs through November 16. Not an estimate that the price will rise.

This is example copy, not a real AAPL prediction or approved recommendation.

### Predictions: #/predictions?symbol=AAPL

Keep the selected-stock heading, return-to-analysis link, panel styling and
existing unavailable/history presentation. The initial adapter reads a real API
response that deliberately says no approved model is available. Do not enable
the old disabled Generate prediction button or add a click-to-train endpoint.
Daily signals will be produced offline, not generated by opening this page.

When a real signal becomes eligible, show these panels in order:

1. **Signal:** stock, target meaning, one supported horizon, rank/call if justified,
   availability, as-of and target trading sessions, publication time.
2. **What it means:** for a relative model, stronger than peers does not necessarily
   mean price up. A percentile is rank, not probability or confidence.
3. **Evidence:** model version and link to same-model performance, coverage and
   limitations. No made-up confidence badge or feature explanation.
4. **History:** dated frozen predictions with pending/resolved status, realized
   outcome where eligible, model/data versions and replay/live labels.

Example ranking card structure (illustrative only):

```text
AAPL                         Relative research signal
Next trading session         Universe percentile: 79
Information through: Nov 16  Target session: Nov 17
Probability: unavailable     Historical reliability: View model performance
Historical replay            Model/version and input snapshot
```

Do not render every optional field as a blank card. Probability stays absent
unless calibration has been established. Market/stock component panels are
deferred: the tested combination did not qualify for absolute direction.

### Model performance: #/performance

Keep the unavailable panel until a real evaluation response exists. A later view
must state target/horizon, model/data versions, evaluation dates, sample size,
coverage, baseline measured on identical observations and known limitations.

For ranking: daily rank IC, top/bottom group spread, fold/time-period breakdown,
decline over time and uncertainty. Explain rank IC in plain language, not as an
accuracy percentage. Label gross research spreads as descriptive, not profit.
For direction: accuracy AND balanced accuracy, class balance and baselines;
probability calibration only when assessed. Never compare relative direction
accuracy with absolute direction as though they answer the same question.

Research reports can be separately published as dated research summaries; do
not label training-period model-selection results as untouched final-test or
live performance. Repeated development-fold exploration remains disclosed.

### Dashboard / watchlists: #/dashboard

Preserve current private account state, owner-keyed items, filtering, open/remove
and refresh persistence. Do not mix one user's cached watchlist into another's.
After signal API is real, a later small summary per saved stock may show signal
availability/rank and freshness. Avoid an unbounded request per stock: use a
bounded batch read or limited initial list. Signal facts may be public, but the
user's watchlist composition remains private through authorizedFetch.

### Methodology: #/methodology

Preserve existing source, indicator and historical-data explanations. Add the
approved target, universe/benchmark definition, cutoff, publication cadence,
price basis, evaluation provenance and survivorship limitations when known.
Explain observed volatility separately from model reliability. Do not invent
a learned risk score because the field exists in a proposed schema.

### Recommendations (later, not part of first increment)

Add only after ranking evidence, coverage and eligibility rules are reviewed.
Use "Stocks to investigate" or "Relative research signals", not Buy/Sell orders.
Initial list: supported stock, eligible rank, target session, freshness and link
to detail/performance. Fixed versioned ordering and bounded pagination; no filters
tuned after observing outcomes. Horizon/risk/sector/watchlist filters are later
work, not justification for creating many empty pages now.

## 4. Response contract and examples

Proposed first endpoint: GET /api/stocks/{symbol}/signals?horizon_sessions=1.
Existing /prices and /indicators contracts remain intact. New schema should be
defined with Pydantic and OpenAPI examples before frontend integration.

  "message": "No approved model signal is available.",
  "target_kind": null,
  "horizon_sessions": 1,
  "as_of_session": null,
  "target_session": null,
  "published_at": null,
  "direction": null,
  "raw_score": null,

  "risk_level": null,
  "model_version": null,

```

  "data_snapshot": "test-fixture-only",
  "provenance": "test_fixture"

```

The fixture demonstrates nullable fields and ranking semantics, not an approved
model or actual probability. Score 0.0012 is a raw return-fraction output, not
a calibrated prediction of exactly +0.12% or 0.12% confidence. The UI need not
display raw_score. Missing dates/version/provenance cannot produce an available
card. A stale stored signal should be explicitly unavailable with its last-known
provenance visible where appropriate; it must not appear to be a fresh call.

| State | API/UI behavior |
| --- | --- |
| Loading | Accessible loading state for this symbol; no previous-symbol signal |
| Available | Render only validated supported fields with target/date meaning |
| No approved model | 200 typed unavailable; informational panel, not server error |
| Insufficient history / missing or unsettled input | Typed unavailable with actionable explanation |
| Stale batch / incompatible artifact | Typed unavailable; never silently reuse as current |
| Unsupported symbol | 404 with existing typed unsupported-symbol behavior |
| Bad horizon / invalid query | 422, no automatic fallback to another horizon |
| Storage failure | Sanitized 503; retry, no fabricated fixture fallback |
| Invalid/misaligned response | Adapter rejects it; controlled unavailable/error display |

The implementer should freeze exact enums with a shared fixture set before code.
No client recomputation of probability, rank, outcome or RSI from visible data.
Preserve nulls; zero and unavailable are different values.

## 5. Frontend adapter and backend connections

```text
Pages.jsx / selected symbol
  -> useSignals(symbol, supported horizon)
  -> GET same-origin /api/stocks/AAPL/signals
  -> Pydantic schema + thin FastAPI route
  -> bounded repository read / unavailable policy
  -> stored model version + prediction batch + immutable prediction
```

The adapter validates schema version, symbol, target meaning, dates, status and
numeric bounds, then creates UI-ready labels. The hook owns cancellation,
10-second timeout/retry behavior and request keys, patterned on use-indicators.js.
Ignore superseded responses after symbol/range changes and unmount. Do not put
backend exceptions or implementation jargon in product messages.

Public signal reads can use normal same-origin fetch. Private watchlist calls
must continue through useAccount()/authorizedFetch with cookies, CSRF,
expected-user headers and account-switch isolation. The browser never connects
to Supabase or Yahoo directly and never receives the database credential.

## 6. Persistence and producer design (later increments)

Reuse existing stocks/price_series/daily_bars instead of creating a parallel
stock store. Add model versions, prediction batches, predictions, outcomes and
evaluations through the next reviewed Alembic revision. Inspect migration head
first. Preserve backend-only privileges/RLS; Supabase browser roles get no grants.

Record symbol, target/horizon, cutoff/target sessions, publication time, source
price basis, scores, model/artifact/data hashes, availability and replay/live
provenance. Unique batch/symbol/target/horizon keys make reruns idempotent.
The original forecast cannot be rewritten after its outcome is observed.
Corrected source data uses explicit versions. Test migrations on disposable
databases before any hosted change; never seed/reset the real hosted database.

Later API candidates: bounded signal history for a stock, prediction detail,
model-specific performance and recommendations. Specify pagination and snapshots
before implementing list pages. No training endpoint or click-to-train UI.

## 7. Current data versus future daily refresh

Current: 506 AAPL historical bars in Supabase; the broad 494-stock research
snapshot lives locally. Connecting Supabase never transfers that snapshot.

Future flow:

```text
Provider adapter -> validated settled daily bars -> database/cache
  -> past-only feature batch -> approved versioned artifact
  -> immutable prediction batch -> FastAPI GET -> React
  -> later outcome resolver -> versioned evaluation records
```

Decide first hosted universe and provider terms/adjustment/freshness before
import or scheduling. Refresh is a job outside chart requests. Use an exchange
calendar for holidays and next sessions, source timestamps, bounded retries,
provisional/settled flags and sanitized job logs. Quotes may refresh more often;
the current model design uses completed daily bars and updates once per session.

The earlier 06:30 New York settled-bar schedule is a proposal, not implemented.
Publication/entry timing is unresolved research: a morning-published signal
cannot promise an executable return starting at the prior close. Model labels,
display wording and any trading-style evaluation must respect that difference.
Daily inference reuses an artifact; retraining is a separate approved process.

## 8. Implementation increments and acceptance

1. **Foundation now:** freeze schema/test fixtures, add real unavailable GET,
   adapter/hook and existing-page state tests. AAPL first, no real model or DB DDL.
2. **Persistence:** reviewed migration, backend-only reads and idempotent imports;
   disposable database tests. No fabricated production predictions.
3. **Hosted data readiness:** selected coverage/import/refresh with provenance,
   calendar and freshness evidence. Do not silently replace hosted sample data.
4. **Model decision later:** resume ML only when Noah asks; evaluation/artifact
   parity and execution timing before any public signal.
5. **Shadow serving:** real offline batch and outcome resolution tested without
   public activation, then limited UI with reliability and rollback support.

Minimum foundation acceptance: route/input/status tests, shared fixture adapter
tests, timeout/cancellation/stale-response cases, selected-symbol navigation,
320/390/1440px overflow and keyboard checks, lint/build. Later acceptance includes
schema/RLS/ownership constraints, artifact/feature parity, idempotency and a frozen
prediction surviving outcome resolution. Label TestClient, live HTTP, database,
browser and real Auth0 evidence separately. New screenshots contain no credentials.
